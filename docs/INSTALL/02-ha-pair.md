# INSTALL 02 — HA pair (Go stack)

Continues [01-standalone.md](01-standalone.md): the pair is assembled from TWO already running standalone nodes.

> **§1–4 are done by the installer** (`deploy/install.sh`): the layout, the `dns-ha` user, the `dns_ha` database with its grants,
> `ha.toml`/`ha-agent.toml`, starting `dns-ha-agent` and `dns-ha-manager`, and `[ha] enabled = true`. They are described below
> as reference — what lies on the node and why. Manual work starts at §5: pairing and pair creation in the panel.

For the mechanics and rationale see [../23-ha-manager.md](../23-ha-manager.md); for the switching rules see
[../22-ha-contract.md](../22-ha-contract.md).

---

## 0. What you get

```
                    http://<service-address>/           ← the panel works ONLY from here
                              │
                       current ACTIVE
              MariaDB rw · PowerDNS primary · service address
                              │  async replication
                          STANDBY
              MariaDB read-only · PowerDNS without a role (no/no)
```

Two processes on each node:

| process | runs as | purpose |
|---|---|---|
| `dns-ha-manager` | `dns-ha` | observes, decides, carries out operations; peer channel to the neighbour (TCP 7901) |
| `dns-ha-agent` | `root` | the only one that touches the node: MariaDB, PowerDNS, the publication address |

The boundary between them is not decoration: the network process has no rights to change the node's role, and the privileged one does not
make decisions.

---

## 1. Layout

The product lives in one tree (see [../23-ha-manager.md](../23-ha-manager.md) §14.4):

```
/opt/dns-panel/{bin,etc,var,www,docs}
/run/dns-panel/ha      HA stack sockets and locks            root:dns-ha    0770
/run/dns-panel/pdns    dns-agent socket                      pdns:www-data  2750
/run/dns-panel/sync    dns-sync-worker wake socket           www-data:dns-ha 2750
/run/dns-panel/pulse   pulse-server control socket           root:www-data  0770
/var/www/vhost/dns-panel → /opt/dns-panel/www
```

The directories in `/run` are created by `etc/tmpfiles/dns-panel.conf`; the system directories (`/etc/systemd/system`,
`/etc/tmpfiles.d`, `/etc/apache2/sites-available`, `/etc/mysql/mariadb.conf.d`, `/etc/powerdns/pdns.d`)
contain only symlinks into `/opt/dns-panel/etc`.

## 2. Accounts and secrets (on each node)

The system user and group `dns-ha`; `www-data` is a member of `dns-ha` — the panel uses the HA IPC sockets and
nothing beyond that. MariaDB: the `dns-ha` user with unix_socket authentication (§3).

**Pair secrets are not created by hand.** None of these files exists on a standalone node, and that is the correct
state:

```
/opt/dns-panel/etc/secrets/peer.key            appears at PAIRING (§5.1); dns-ha:dns-ha 0600
/opt/dns-panel/etc/secrets/repl.secret         appears at PAIR CREATION (§5.3); root:root 0600
/opt/dns-panel/etc/secrets/ha_monitor.secret   appears at PAIR CREATION (§5.3); root:root 0600
```

`peer.key` is derived by the nodes themselves during pairing; it is not sent over the network at all. The replication passwords
are generated by the donor and passed to the neighbour encrypted; the `repl` and `ha_monitor` accounts are created by the agent on
both nodes at pair creation. A person does not type or copy a single secret.

`peer.key` signs commands between nodes (HMAC). Traffic is not encrypted, but a command cannot be forged without the key;
the few things that must travel secretly (passwords) are encrypted separately with a key derived from it.

## 3. Local DB `dns_ha`

Not replicated — on purpose: it holds what is specific to each node (the operation log, configuration
revisions, the state projection, the node UUID). The installer creates the database and grants the privileges:

```sql
CREATE USER IF NOT EXISTS 'dns-ha'@'localhost' IDENTIFIED VIA unix_socket;
GRANT ALL PRIVILEGES ON dns_ha.* TO 'dns-ha'@'localhost';
GRANT READ_ONLY ADMIN, SLAVE MONITOR ON *.* TO 'dns-ha'@'localhost';
```

The manager applies the schema itself at startup (it is embedded in the binary). Data privileges — only on `dns_ha`. Two
global ones without data access: `READ_ONLY ADMIN` (on STANDBY the database is read-only, and the manager must write its own
`dns_ha`) and `SLAVE MONITOR` (`SHOW REPLICA STATUS`; without it the manager says "replication not observed", and
the pair cannot be assembled). `DROP DATABASE dns_ha` takes the database grants with it — when recreating it by hand, grant them again
(§5.4), otherwise the manager does not start, failing with "CREATE command denied".

BINLOG ADMIN and SUPER are not needed: `dns_ha` does not get into the binlog, because it is excluded by the node configuration
(`etc/mariadb/dns-panel.cnf`):

```ini
binlog_ignore_db         = dns_ha
replicate_ignore_db      = dns_ha
```

## 4. Node configuration

There is NO identity in the configs: on first start the node issues itself a UUID and stores it in ITS OWN local
`dns_ha` (table `ha_identity`). Name, site and description are metadata; they live in the pair configuration and are edited in
the panel.

`/opt/dns-panel/etc/ha.toml` (manager, `root:dns-ha 0640`) — only access to its own DB:

```toml
[database]
socket   = "/run/mysqld/mysqld.sock"
database = "dns_ha"
```

`/opt/dns-panel/etc/ha-agent.toml` (agent, `root:root 0600`) — access to the node:

```toml
[mysql]
socket = "/run/mysqld/mysqld.sock"
user   = "root"

[replication]
user             = "repl"
secret_file      = "/opt/dns-panel/etc/secrets/repl.secret"
port             = 3306
dump_user        = "ha_monitor"
dump_secret_file = "/opt/dns-panel/etc/secrets/ha_monitor.secret"
databases        = ["dns_panel", "pdns"]

[pdns]
role_conf = "/etc/powerdns/pdns.d/90-ha-role.conf"

[publication]
# Empty: the service address lives in the replicated pair configuration and arrives in the publication command.
```

The agent has no `node` key (it is rejected at startup). Defaults that are usually not changed:
`peer_key.path`/`peer_key.owner`, `panel_secret_group` (the web process group — `auth-master.key` must remain
readable by the panel), `failsafe.source`/`failsafe.link` (`etc/mariadb/ha-failsafe.cnf` →
`/etc/mysql/mariadb.conf.d/61-dns-panel-ha.cnf`).

The PowerDNS role — `primary` and `secondary` as a pair — is stored ONLY in `/etc/powerdns/pdns.d/90-ha-role.conf`
([01 §3](01-standalone.md#3-why-powerdns-is-configured-this-way)). In a pair the agent keeps ACTIVE at `yes/yes`, STANDBY at
`no/no`; dismantling the pair returns both nodes to `yes/yes`. A role change is one PowerDNS restart with the readiness probe
closed. A role set anywhere else would override the role file: the agent would then fail to prove STANDBY
(`role_unverified`) and, for safety, stop PowerDNS. The installer finds such a role and stops;
the same check by hand:

```bash
sudo grep -Hn '^\s*\(primary\|secondary\|master\|slave\)\s*=' /etc/powerdns/pdns.conf /etc/powerdns/pdns.d/*.conf
# exactly two lines are expected, both from 90-ha-role.conf
```

## 5. Creating the pair

The pair is assembled from two RUNNING standalone nodes, with no pair description file, no manual secret and no config
edits.

**In the panel** this is the High availability section on both nodes: on the first, "Open pairing on this node"; on the second,
"Join existing pair" with the first node's address, then comparing six digits and Approve. After confirmation the same place
shows an inventory of both sides' data; you choose whose data stays, and the pair is created. Below are the same steps
on the command line — they do exactly the same thing (the panel talks to the same manager via
`/run/dns-panel/ha/manager.sock`, so the commands run as `dns-ha`):

```bash
M="sudo -u dns-ha /opt/dns-panel/bin/dns-ha-manager"
```

### 5.1 Pairing: the nodes start trusting each other

A fresh node does NOT expose the pairing interface: until a person opens the window, all commands are rejected.

```bash
# A (where the decision is made): open the window
$M -pair create

# B (the one asking to join): ask to join A
$M -pair join -address 10.0.0.1
#   → prints six digits

# A: see who is asking and COMPARE THE DIGITS BY EYE
$M -pair status
#   state=pending, code=418302, peer_node_id=…, hostname (claimed), peer_address (observed)

# A: the digits match — approve
$M -pair approve
```

After `approve` both nodes have the same `peer.key`, and each knows whom it shares it with. If
the digits do not match — `-pair reject`, and both nodes stay exactly where they were. An interrupted attempt is cleared by
`-pair reset`; trust that is already established is removed only explicitly (`-pair reset -force`).

There is no pair yet: each node has its own data and its own work.

### 5.2 Whose data stays

```bash
$M -pair inventory
```

Shows both sides at once: which databases exist and how many rows they hold. The RECEIVER's data will be replaced
by the donor's data — there is no merging of two databases. If only one node has data, the donor is obvious; if both do,
a person makes the decision by looking at this inventory.

### 5.3 Creating the pair

The command runs on the DONOR — the node whose data stays:

```bash
$M -pair build -provider floating_ip -address 10.0.0.10/32
# anycast: $M -pair build -provider anycast -address 10.0.0.53/32 -probe-port 17900
```

What happens step by step (see [../23-ha-manager.md](../23-ha-manager.md) §14.6):

```
replication secrets → grants on both → reseed of the receiver from the donor
→ TOTP encryption key → fail-safe and revision 1 on both (epoch 1)
→ donor ACTIVE, receiver STANDBY, the service address comes up
```

The interface for the service address is not asked for: each node determines its own (if the address is already up, that is its
interface; otherwise the one whose subnet the address belongs to). Network card names on the two machines do not have
to match.

Until the reseed, the receiver's data is untouched: any failure before it leaves BOTH nodes running as standalone
nodes. The command ends with a replication check: `IO=Yes`, `SQL=Yes` and a converged position. To retry an
interrupted attempt, run the same command with `-id <the same>`: the reseed is not performed a second time.

`-provider marker` means "someone outside manages the address" (a BGP daemon, a load balancer) — then
`-address` is not needed.

### 5.4 Rebuilding the pair from scratch

If the pair is assembled again on nodes where it already existed, the previous pair's state must be removed entirely — otherwise
the new one inherits foreign epochs and foreign history. On both nodes:

```bash
sudo systemctl stop dns-ha-manager dns-ha-agent
sudo mysql -e "STOP SLAVE; RESET SLAVE ALL; SET GLOBAL read_only=0;"
# DROP takes the database grants with it; READ_ONLY ADMIN and SLAVE MONITOR (on *.*) remain
sudo mysql -e "DROP DATABASE dns_ha; CREATE DATABASE dns_ha; GRANT ALL PRIVILEGES ON dns_ha.* TO 'dns-ha'@'localhost';"
sudo rm -f /opt/dns-panel/var/{safety.json,agent-state.json}                # the previous pair's epoch
sudo rm -f /opt/dns-panel/etc/secrets/{peer.key,repl.secret,ha_monitor.secret}
sudo rm -f /etc/mysql/mariadb.conf.d/61-dns-panel-ha.cnf                    # the previous pair's fail-safe
sudo mysql -e "FLUSH BINARY LOGS; PURGE BINARY LOGS BEFORE NOW();"          # history that the new pair does not have
sudo systemctl start dns-ha-agent dns-ha-manager
```

`dns_panel` and `pdns` on the future donor are KEPT — they are what gets copied to the receiver.

## 6. Service address

The panel is served at ONE address, which lives on the current ACTIVE. The address is set in the pair configuration
(`publication.params` of the revision).

**Floating IP** — the agent brings the address up and down, confirming the result by reading the interface, and sends
gratuitous ARP on a move.

**Anycast** — a `/32` address on `lo` of both nodes; what moves is not the address but the route: the readiness probe (TCP, by
default 17900) is open only on ACTIVE, and based on it the external network keeps the route to it — Cisco IP SLA + track,
BGP or [dns-watcher](reference/07-dns-watcher.md).

In `etc/panel.toml` there is exactly one switch about the pair, `[ha] enabled = true` (set by the installer; it means
"the stack is installed", not "the pair is created"). Everything else about the pair (who we are, who the neighbour is, the service address, the role)
the panel asks `dns-ha-manager`.

The node addresses remain management addresses: on STANDBY the panel cannot even create a session (MariaDB is read-only), and
the login page redirects to the service address.

## 7. Verification

The state of both nodes — the High availability page. As seen by the manager (on each node):

```bash
echo '{"cmd":"status"}' | sudo -u dns-ha nc -U /run/dns-panel/ha/manager.sock

# ACTIVE: role=active, route_announced=1, ha_healthy=true, decision.reason=steady_active
# STANDBY: role=standby, route_announced=0, replication IO/SQL=Yes
```

```bash
curl -s http://<service-address>/health/ready     # on ACTIVE: "ready":1
ip -br -4 a                                       # Floating IP: the publication address only on ACTIVE
```

A planned switchover — from ACTIVE (the panel, the High availability page, or directly):

```bash
sudo -u dns-ha /opt/dns-panel/bin/dns-ha-manager -switchover
```

Expected behaviour: for a few seconds the pair does not accept writes, the service address moves, the new ACTIVE is ready
in 7–12 s.

## 8. Emergency paths

| situation | action (`dns-ha-manager …`, as `dns-ha`) |
|---|---|
| ACTIVE is unreachable, the role is needed here | `-emergency -ack <reason> -operator <who>`; reasons: `old_active_database_stopped`, `old_active_host_down`, `operator_isolated`; the neighbour is fenced |
| the node is fenced (`RESEED_REQUIRED`) | `-reseed` — the node's data is erased and reloaded from ACTIVE, the role does not change |
| an operation was interrupted | `-resume -id <operation>` — continues from the interrupted step, completed steps are not repeated; `-operation` shows the current one |
| the panel is unavailable | the same commands from the command line; HA does not depend on the web stack |

Emergency promotion NEVER happens on its own: a two-node pair cannot tell "the neighbour died" from "the network
broke", so a person makes the decision, and the reason is recorded in the operation log.
