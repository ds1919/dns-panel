# 25 — NS Pulse: тестеры и переключение записей

NS Pulse проверяет доступность конкретных адресов с удалённых площадок и по результатам переключает
RRset'ы в зонах панели. Второй его режим — **Pinger** (медленный сбор): неспешный обход всех адресов A/AAAA,
чтобы видеть, какие из них давно не отвечают.

Связано: [22-ha-contract.md](22-ha-contract.md) и [23-ha-manager.md](23-ha-manager.md) (право писать),
[24-dns-engine.md](24-dns-engine.md) (путь правки записей), [16-delivery.md](16-delivery.md) (кому уезжают
зоны). Установка — [INSTALL/01-standalone.md](INSTALL/01-standalone.md), раздел «NS Pulse». Код: `src/dns-pulse`,
`libexec/pulse-apply.pl`, раздел NS PULSE в `www/include/functions.pm`, `www/js/pulse.js`.

---

## 0. Что умеет и чего нет

- проверки **ICMP** и **TCP connect** по конкретному IP (не по имени: проверка переключаемого имени после
  первого переключения проверяла бы уже другой хост). Прикладных проверок (HTTP и т.п.) нет;
- проверка назначается **группам** тестеров (многие-ко-многим); см. оговорку о поимённом назначении в §6;
- правило у RRset: **упорядоченные ветки** «если условия — опубликовать такой-то набор», внизу всегда
  «иначе — основной набор»; условия по состоянию проверки и по расписанию;
- история — полоски состояний (интервалы в MariaDB, отдельного хранилища метрик нет);
- Pinger — только наблюдение, правил он не создаёт и на DNS не влияет.

Разных ответов разным сетям (`view` BIND), весов и географии нет: правило меняет обычную зону, изменение
получают все её получатели. Агент ничего не знает о зонах и записях — только адреса.

## 1. Части

| Часть | Где | Что делает |
|-------|-----|------------|
| `pulse-server` (Go) | узел панели | принимает агентов, раздаёт задания, пишет состояния в `dns_panel`, держит сроки, решает о переключении |
| `pulse-agent` (Go) | любая площадка | сам подключается к серверу, выполняет пробы, шлёт только переходы; участвует в Pinger |
| `libexec/pulse-apply.pl` | узел панели | запускается сервером; переключает набор через `pdns_apply_rrsets` или сверяет зону (`--verify`) |
| страница NS Pulse | панель | вкладки **Agents / Checks / Rules / History** |
| колонка Pulse, точка Pinger | страница записей | вход в правило RRset и в историю адреса (§6, §7) |
| Settings → **Pinger & Pulse** | панель | параметры Pinger, заготовка новой проверки, срок истории |

Сетевых проверок в веб-запросах панели нет. Бинарники собираются `make -C src/dns-pulse build`
(статические, `CGO_ENABLED=0`); агент — стандартная библиотека + `x/net/icmp`, сервер — ещё драйвер MySQL.

### Конфиг агента

```toml
server      = "10.0.0.10:7902"
enroll_key  = "…"      # общий ключ площадки
fingerprint = ""       # SHA-256 сертификата сервера (64 hex); пусто — запомнить при первом соединении
log_level   = "info"   # debug | info | warn
#[reconnect]           # пауза переподключения, по умолчанию 1s…30s
#min = "1s"
#max = "30s"
```

Любой другой ключ — ошибка запуска: цели, интервалы и пороги приходят только из панели. Файл одинаков на
всех машинах: личного секрета, имени и id в нём нет. Готовый файл (адрес, ключ, отпечаток) показывает
**NS Pulse → Agent config**; адрес сервера хранится в `settings.pulse_server_address` и задаётся там же.
Флаг `-no-icmp` запрещает агенту ICMP даже при наличии прав. Лог — в stdout (journald).

### Приход агента

1. При первом запуске агент создаёт ключ `agent.key` в `StateDirectory` (64 hex) и печатает в журнал код
   вида `7F3A-91C2` — первые 8 знаков SHA-256 ключа. Сервер хранит только хэш (`pulse_testers.key_hash`).
2. Неизвестный ключ с верным `enroll_key` — заявка: строка в `pulse_testers` без `approved_at`, ответ
   `goodbye "waiting for approval in the panel"`. Повторные подключения обновляют ту же строку.
3. Человек видит заявку (имя хоста, адрес, код) в **Agents → Waiting for approval**, подтверждает, даёт имя
   и место. Имя агент узнаёт из `welcome`.

До подтверждения заданий и записи результатов нет. `enroll_key` хранится открыто (`pulse_enrollment`) и
даёт только место в очереди; смена ключа (`POST /pulse/enrollment/key`) закрывает дверь неподтверждённым
и не трогает подтверждённых. Удаление тестера — «забыть»: работающий агент вернётся заявкой.

Адрес, с которого пришёл агент, пишется в `pulse_testers.addr` и показывается; опознаёт агента только ключ.

### TLS и отпечаток

TLS включён всегда (минимум TLS 1.2). Сервер при первом старте генерирует самоподписанный сертификат
(ECDSA P-256, 10 лет) и кладёт его в `pulse_server_tls` — сертификат принадлежит **паре**, реплицируется
вместе с `dns_panel`, поэтому смена ролей HA не меняет отпечаток.

Агент имя в сертификате не проверяет, сверяет SHA-256 DER-сертификата:

- явный `fingerprint` в конфиге всегда главнее запомненного;
- пустой — запоминается при первом соединении (`server.fingerprint` в `StateDirectory`, атомарно, до
  отправки ключа); дальше требуется тот же, при смене — отказ с сообщением о подмене;
- протокол поддерживает «следующий отпечаток»: `next_fingerprint` от сервера сохраняется рядом с текущим,
  агент отвечает `fingerprint_ack`; после первой полной сессии с новым он становится текущим.
  **Сервер `next_fingerprint` пока не отправляет** — ротация сертификата сейчас требует правки агентов.

### Права агента на ICMP

Юнит `pulse-agent.service`: не root, `AmbientCapabilities=CAP_NET_RAW`, `NoNewPrivileges`. Подойдёт и
unprivileged ping socket (`net.ipv4.ping_group_range`). Агент проверяет возможность ICMP при старте и
сообщает её в `hello`; без ICMP сервер не выдаёт ему ICMP-задания (пара остаётся без данных → `unknown`), а
в Pinger агент не участвует. Нехватка прав никогда не превращается в `down`.

### Переподключение

Обрыв — штатное состояние (сервисный адрес переезжает между узлами). Агент переподключается с растущей
паузой (`reconnect.min…max`), **проверки продолжаются** — они принадлежат процессу, не соединению, и
гистерезис не сбрасывается. После подключения агент отсылает текущее состояние всех проверок. Очередь
отправки хранит последнее сообщение каждого вида (последнее состояние по каждой проверке), поэтому
накопленное за обрыв не проигрывается.

## 2. Право менять DNS

- `pulse-server` спрашивает роль у `dns-ha-manager` (`{"cmd":"status"}` по `ha.socket`) на рукопожатии,
  на **каждом** сообщении агента, при срабатывании сроков и пересчётах. Ответ кэшируется на
  `timeouts.ha_verdict_ttl` (1 с). Нет ответа или `ha_configured` неизвестен — отказ. `ha.enabled = false`
  (узел без HA) — наблюдать можно всегда.
- «Вправе наблюдать» = роль `active` (или HA не настроен). Идущая HA-операция наблюдению не мешает: она
  замораживает запись в зоны, а не приём результатов.
- **На STANDBY агентов не принимают**: `goodbye "this node is not active — connect to the service address"`.
  Потеряв роль, сервер снимает все сроки, выдержки, повторы, пересборки Pinger и рвёт потоки агентов.
- Запись в зону делает только `pulse-apply.pl` через `pdns_apply_rrsets` (транзакция, serial, аудит).
  Право на запись он спрашивает сам, той же `ha_write_verdict`, что и панель; `skip` (не наш узел,
  заморозка) и `fail` — отказ, сервер повторит переключение с растущей паузой.
- Агенты DNS не правят: они сообщают, что видели.

## 3. Протокол агент ↔ сервер

Одно долгое TLS-соединение, JSON-объект с полем `type` на строку (до 1 МиБ), `internal/wire`. Не gRPC.

| Сообщение | Кто | Содержимое |
|-----------|-----|-----------|
| `hello` | агент | `agent_key`, `enroll_key`, `hostname`, `run_id`, `version`, `can_icmp`, `can_ipv4`, `can_ipv6` |
| `welcome` | сервер | `tester_id`, `tester_name`, `confirm_every_seconds` |
| `assign` | сервер | `tasks[]` — полный набор: `check_id`, `config_version`, `kind`, `target_ip`, `port`, `interval_seconds`, `timeout_ms`, `probes_per_run`, `ok_probes_required`, `fail_threshold`, `ok_threshold` |
| `accepted` | агент | `checks[]` (`check_id`, `config_version`) — принятый набор |
| `transition` | агент | `check_id`, `config_version`, `state` (`healthy`/`degraded`/`down`), `detail` |
| `confirm` | агент | `checks[]` — что выполняется сейчас; пустой список тоже шлётся |
| `next_fingerprint` / `fingerprint_ack` | сервер / агент | ротация отпечатка (§1) |
| `sweep_claim` / `sweep_batch` / `sweep_result` | Pinger (§7) | |
| `goodbye` | сервер | `reason` |

```text
{"type":"hello","agent_key":"…","enroll_key":"…","hostname":"cn-probe-01","run_id":"…","can_icmp":true}
← {"type":"welcome","tester_id":1,"tester_name":"msk-1","confirm_every_seconds":30}
← {"type":"assign","tasks":[…]}
{"type":"transition","check_id":7,"config_version":3,"state":"down"}
{"type":"confirm","checks":[{"check_id":7,"config_version":3}]}
```

Причины `goodbye`: `waiting for approval in the panel`, `enrollment key rejected`, `this tester is switched
off in the panel`, `this tester is no longer allowed to report`, `superseded by a newer connection`,
`check-in interval changed — reconnect for the new one`, «узел не активен» (§2).

**Измерений агент не шлёт** — только переходы, состояние после (пере)подключения и подтверждения.
Отметки времени ставит сервер.

**Подтверждение по заданиям.** `confirm` раз в `confirm_every_seconds` = `confirm_max_age_seconds / 3`
(не меньше 1 с). Свежесть хранится у пары (`pulse_results.confirmed_at`) и двигается результатом по паре
или подтверждением, где пара указана с **текущей** `config_version`; живое TCP-соединение свежести не даёт.

**Версия задания** (`pulse_checks.config_version`) растёт, только когда меняется измерение: вид, адрес,
порт, интервал, предел, пробы, пороги. Переименование, выключатель и состав исполнителей её не меняют.
При росте версии панель сразу переводит пары в `unknown/stale_config`; результат по старой версии сервер
игнорирует.

**Доставка правок.** Сигнала «задания изменились» от панели агенту нет. Сервер сравнивает список в
каждом `confirm` с действующим набором и при расхождении шлёт `assign` целиком — правка доезжает не
позже чем через `confirm_every_seconds`. Агент применяет набор целиком; проверку с той же версией не
перезапускает.

**Один тестер — один поток.** Новое подключение вытесняет прежнее; сервер отмечает каждый поток своим
поколением и на каждом сообщении проверяет, что поток текущий, иначе — `goodbye` без записи. `run_id`
(новый на каждый запуск процесса) нужен человеку: вытеснение с другим `run_id` пишется в журнал сервера
как «рядом работает вторая копия». На карточке тестера это не показывается.

**Отзыв.** На каждом сообщении сервер перечитывает строку тестера: удалён, выключен, не подтверждён или
сменился ключ — `goodbye` и разрыв; изменился `confirm_max_age_seconds` — разрыв, новый интервал придёт с
новым `welcome`. Отдельного сигнала панели на разрыв потока нет: отозванного агента отрезает его же
следующее сообщение (не позже `confirm_every_seconds`).

## 4. Состояния

Состояние пары «проверка × тестер» считает **агент** (`internal/probe/state.go`). Один прогон =
`probes_per_run` проб подряд:

```text
все пробы ответили                        → чистый прогон
ответили хотя бы ok_probes_required       → частичный (не копит ни отказ, ни восстановление)
меньше                                    → неудачный

fail_threshold неудачных подряд  → down
ok_threshold чистых подряд       → healthy
иначе                            → degraded   (в том числе сразу после старта проверки)
```

На сервере у пары четыре состояния: `healthy`, `degraded`, `down`, `unknown`. У `unknown` есть причина
(`unknown_reason`), решение на неё не смотрит:

| Причина | Когда |
|---------|-------|
| `no_result_yet` | пара только появилась или проверку/тестера включили обратно |
| `silent` | истёк срок подтверждения (§5) |
| `stale_config` | измерение изменилось, результата по новой версии ещё нет |
| `disabled` | оператор выключил тестера или проверку |

Строка `pulse_results` существует ровно пока существует пара (проверка назначена группе, где состоит
тестер); заводит и удаляет её панель при назначении проверки, смене состава группы и удалении группы
(`_pulse_sync_results`), удаление проверки или тестера уносит строки каскадом. Выключатель пару не
удаляет, а переводит в `unknown/disabled`; задания выдаются только если включены обе стороны.

«Тестер молчит» — это `unknown`, а не «хост умер»: потеря наблюдения DNS не двигает (§6).

Состояние самого агента — отдельно: `pulse_testers.state` = `online` / `silent` / `disabled`. `online`
ставит только подтверждение; включение тестера обратно даёт `silent` до первого подтверждения.

## 4.1. История

Хранятся только **закрытые** интервалы; текущий отрезок — это `state` + `since` в текущей строке:

| Что | Закрытые интервалы | Текущий отрезок |
|-----|--------------------|-----------------|
| пара | `pulse_intervals` | `pulse_results.state`, `since` |
| агент | `pulse_tester_intervals` | `pulse_testers.state`, `state_since` |
| адрес Pinger | `pulse_sweep_intervals` (`ended_by` — кто увидел смену) | `pulse_sweep_targets.last_state`, `state_since` |
| переключения | `pulse_rule_events` (+ `pulse_rule_event_checks`) | — |

Переход пишется одной транзакцией под `SELECT … FOR UPDATE` строки пары; прежнее состояние читается под
той же блокировкой. Переход в то же `state` — не переход (сравнивается только `state`, не причина).
Конец интервала никогда не раньше его начала.

**Срок хранения** — `pulse_history_days` (по умолчанию 90, 1…3650). Подрезка попутная: закрылся интервал
объекта — удаляются старые интервалы этого же объекта; записалось событие правила — старые события этого
правила. Фоновой чистки нет, поэтому затихший объект сохраняет свои старые интервалы. Нет строки настройки
или значение негодное — ничего не удаляется.

**Экран.** Вкладка History: полоска на проверку за 1d / 1w / 1m (`GET /dns-api/pulse/history?window=`),
раскрытие по агентам, метки переключений DNS. Цвет полоски проверки — худший ответ её агентов в каждый
момент; серый — никто не ответил, штриховка — пару не наблюдали. Суточная полоска есть в таблицах Checks и
Agents и у условий в редакторе правила. Живых обновлений нет: полоска верна на момент открытия.

## 5. Сроки

| Настройка | Где | По умолчанию |
|-----------|-----|--------------|
| интервал, предел ответа, пробы/нужно ответов, порог отказа/восстановления | проверка | 5 с, 1000 мс, 3/1, 3/3 (заготовка — Settings → New check defaults) |
| выдержка ветки («держится N с») | ветка правила | 30 с |
| выдержка возврата на основной набор | правило | 300 с |
| `confirm_max_age_seconds` — сколько подтверждение считается свежим | тестер | 90 с |

Значения вне пределов у проверки, тестера и правила панель приводит к границе (`_pulse_int`), в Settings —
отказывает с причиной. Срок `confirm_max_age_seconds` — это и то, сколько сервер готов решать по
устаревшим данным: канал к агенту упал вместе с целью — до истечения срока правило видит прежнее
`healthy`. У тестеров из переключающих правил его стоит держать коротким.

**Периодических обходов нет.** Вместо них — таймер на конкретный момент:

- у пары: `confirmed_at + confirm_max_age`; каждое подтверждение или результат переставляет его;
  сработал — пара `unknown/silent`, интервал закрыт моментом, когда знание кончилось;
- у агента свой таймер от `last_confirm_at` (у тестера без заданий парных сроков нет); сработал — `silent`;
- таймер заводится только если обе стороны включены и `confirmed_at` не пуст;
- сработавший раньше настоящего срока таймер переставляется на настоящий; неудачная запись повторяется
  с паузой `timeouts.retry_min…retry_max` (1 с…1 мин);
- истечение — тоже событие: пересчитываются правила, которые смотрят на эту пару/этого агента.

**Холодный старт** (`Activate`): до открытия порта сервер расставляет все сроки по базе (просроченные
срабатывают сразу), запускает полный пересбор целей Pinger и пересчитывает все включённые правила. На
старт отведено `timeouts.db + timeouts.apply`; не прочитались сроки — демон падает, не прошёл пересчёт —
работает дальше, правила стоят на повторе. На узле без роли `Activate` ничего не делает.

**Смена роли.** `dns-ha-agentd` после успешных `promote` и `emergency_promote` шлёт на управляющий сокет
`activate`, после `demote` — `deactivate` (в фоне, с повторами; нет сокета — молча). `activate` = тот же
`Activate`; ответ `{"ok":true}` только когда сроки расставлены и правила решены. `deactivate` ещё раз
спрашивает роль и, если узел не активен, снимает сроки, выдержки, пробуждения и потоки. Кроме того, первое
же рукопожатие агента на новом активном узле вызывает `Activate`. Путь сокета у `dns-ha-agentd` зашит
(`/run/dns-panel/pulse/control.sock`); если в `pulse-server.toml` он другой, сервер пишет в журнал
предупреждение, что сигналы о смене роли не придут.

## 6. Правило Pulse

Правило принадлежит **RRset** (зона + имя + тип) и управляет набором значений целиком. Типы: `A AAAA
CNAME MX NS SRV TXT` (`@PULSE_RR_TYPES`); зона должна быть доступна на запись (не SLAVE). Одно правило на
RRset (`UNIQUE(domain_id, rr_name, rr_type)`). Pulse не знает, что такое IP: ветка публикует набор, у MX
это может быть просто другой приоритет. У CNAME набор ровно из одного значения. Содержимое проверяет
`dns_validate`, как у обычных записей.

**Вход.** На странице записей колонка **Pulse** (видна с правом `pulse.manage`) у каждого RRset
поддерживаемого типа: `off` / `default` / `rule N` / `switched` / `held`; щелчок открывает редактор
правила поверх страницы (`/pulse?rule=N` или `/pulse?zone=…&name=…&type=…`). Открытие ничего не создаёт:
правило появляется в базе при первом сохранении, **выключенным**, с основным набором = текущее
содержимое зоны. Вкладка **Rules** на странице NS Pulse — список настроенных правил с отбором; оттуда же
настройку можно скопировать на другие записи (до 100 за раз; логика копируется всегда, значения — только
для того же типа).

**Ветки** проверяются сверху вниз, внизу всегда «иначе — основной набор»:

```text
1. Если ЛЮБОЕ:  ICMP 10.20.20.1 unavailable (all agents)
                TCP 10.30.30.1:8080 unavailable (any agent)
   → опубликовать 10.10.10.2, если держится 30 с
2. Если ВСЕ:    TCP 10.30.30.2:8080 unavailable (at least 2 agents)
                расписание: пн–пт 09:00–18:00
   → опубликовать 10.10.10.3, если держится 30 с
иначе → основной 10.10.10.1, если держится 300 с
```

Условия двух видов:

1. **Проверка**: `expect` = `available` (healthy) / `degraded` / `unavailable` (down); `NOT` нет.
   Наблюдатели условия — **все** исполнители проверки (`pulse_condition_testers`, пересобираются панелью
   при каждой смене назначения и состава групп). Согласие наблюдателей `agg`:

   | `agg` | истинно | ложно | иначе |
   |-------|---------|-------|-------|
   | `any` | хоть один ответил как ждём | все ответили иначе | неизвестно |
   | `all` | все ответили как ждём | хоть один иначе | неизвестно |
   | `at_least N` | как ждём ≥ N | даже с молчащими N не набрать | неизвестно |

   Пара в `unknown` — «нет ответа», не «нет». Наблюдателей нет — неизвестно. Редактор предлагает `all`;
   `N` не больше числа исполнителей.
2. **Расписание**: дни недели (`days_mask`, биты пн…вс), окно времени `HH:MM` (обе границы, через полночь
   можно), даты с/по. Часовой пояс один на правило (`schedule_tz`, по умолчанию UTC; неизвестный пояс →
   UTC). Расписание всегда разрешимо.

Ветка соединяет условия `any` (OR) или `all` (AND), вложенности нет:

| Ветка | `any` | `all` |
|-------|-------|-------|
| выполнена | хоть одно истинно | все истинны |
| не выполнена | все ложны | хоть одно ложно |
| неизвестна | иначе | иначе |

Действует первая выполненная ветка; основной набор — только если все ветки выше подтверждённо не
выполнены. **Неизвестная ветка останавливает разбор: запись остаётся как есть** (`rules.Decide` → `nil`).
Ветка без условий — неизвестна (сохранить такую нельзя, но она может опустеть каскадом при удалении
проверки).

**Выдержка.** Решение отличается от опубликованного → таймер на выдержку цели (ветки или
`default_hold_seconds`). Цель сменилась — отсчёт заново; решение стало «неизвестно» или совпало с
опубликованным — таймер снимается. По истечении решение принимается заново и только тогда вызывается
`pulse-apply.pl --rule N [--branch M] --reason …`. Неудача применения повторяется с растущей паузой без
повторной выдержки.

**Когда пересчитывается** — только по событию: переход пары, истёкший срок, граница расписания (таймер до
ближайшей границы окна или полуночи), сигнал панели `recompute` (сохранение правила, веток, проверки,
тестера, состава групп), `activate`. Неудавшийся пересчёт повторяется с паузой `retry_min…retry_max`.

**Применение** (`pulse_rule_apply`, под `FOR UPDATE` строки правила): правило выключено — отказ; уже в
нужном состоянии — ничего; зона уже содержит нужный набор — правится только учёт, без SOA bump; иначе
`pdns_apply_rrsets` с `REPLACE`, затем отметка `published`, событие в `pulse_rule_events` и запись
`pulse_switch` в аудит. Порядок: сначала зона, потом отметка.

**Ручная правка управляемой записи** отбивается в `pdns_apply_rrsets` (кроме пути `pulse`), то есть и из
UI, и через API/MCP: «… is managed by NS Pulse — switch the rule off to edit it by hand».

**`held`.** Перед записью и при каждом пересчёте без переключения (`--verify`) опубликованный набор
сравнивается с зоной как множество канонических значений. Расхождение (зону правили мимо панели) — правило
уходит в `held`, пишется `pulse_held` в аудит, обработчик его больше не трогает. Пустой `published`
(после пересохранения веток) расхождением не считается.

**Выключение и включение.**

- Выключение не трогает зону: опубликованное остаётся, запись снова правится руками.
- Включение требует хотя бы одну ветку, ни одной ветки без условий и ни одного условия без исполнителя.
- Включение правила, стоявшего на основном наборе, переснимает основной набор с зоны.
- Включение из `switched` или `held` наборы не трогает: состояние выводится сверкой зоны с наборами —
  совпало с основным → `default`, с веткой → `switched` ею, ни с чем → `switched` без ветки, и обработчик
  публикует текущее решение. Так выключить-включить — это выход из `held` с возвратом записи под Pulse.
- Сохранение веток пересоздаёт их и тем же способом выводит состояние.

Удаление правила зону не трогает.

**Предпросмотр в редакторе.** Разбор стартует от живых состояний пар (`pulse_rule_get` отдаёт
`live_state`), можно примерить состояние условия («what-if»): меняется только вывод, у ветки появляется
пометка предпросмотра, в DNS ничего не уходит. Если `pulse-server` не отвечает на управляющем сокете,
страница пишет «The Pulse server is not running on this node — nothing is being switched».

**Группы и исполнители.** Группа — набор тестеров для задачи, не локация и не `view`. Исполнители
проверки в панели = агенты её групп ∪ назначенные поимённо (`pulse_check_agents`), без дублей
(`_pulse_runners_sql`). **Расхождение:** `pulse-server` выдаёт задания только через группы
(`store.Tasks`), и проверка условий перед включением правила тоже смотрит только группы — поимённо
назначенный агент задания не получает.

## 7. Pinger (медленный сбор)

**Цели** — адреса из включённых записей A/AAAA зон панели: primary, а secondary тоже, если включено
**Settings → Pinger & Pulse → Include secondary zones** (`pulse_sweep_secondary`); один адрес в нескольких записях —
одна цель (`pulse_sweep_targets`, ключ `target_ip + net_scope`, область пока одна — `default`). Ссылка
«адрес в этой записи» — интервал `pulse_sweep_refs` (`since…until`), ссылки не удаляются.

**Список ведёт путь записи:** после каждого `pdns_apply_rrsets` и удаления зоны вызывается
`pulse_sweep_after_write` шлёт pulse-server `{"cmd":"sweep","zone":N}`, и он (`internal/store/sweepsync.go`)
пересобирает ссылки зоны под именованным замком `psweep:<id>`; A/AAAA читаются под замком из базы PowerDNS
своей учёткой `dns-pulse` только на чтение. Адрес ушёл из всех записей — последний ответ закрывается интервалом, цель
помечается `unref_at`, аренда снимается с подъёмом поколения; вернулся — та же цель с историей, но без
свежести (идёт в очередь первой). Цель без ссылок дольше `pulse_history_days` удаляется целиком.

Пересборка не удалась — зона помечается в `pulse_sweep_dirty` (если демон не слушает, помечает панель). Демон
помнит зону и повторяет помеченные с паузой `retry_min…retry_max`; на старте, при `activate` и при смене настройки
secondary (`{"cmd":"sweep","all":true}`) — полная пересборка всех зон, у каждой зоны свой лимит времени.

Secondary-зоны меняются передачей, которую панель не видит. На check-in агента (не чаще раза в минуту)
pulse-server сравнивает SOA каждой secondary с прошлым разом и пересобирает зоны, у которых SOA сменился. Всё это
только на активном узле; понижение обрывает идущую пересборку.

**Очередь** — через тот же поток агента, только по просьбе агента:

```text
агент  → sweep_claim
сервер → sweep_batch: sweep[] {target_id, generation, ip, timeout_ms, probes}, sweep_parallel
         или пустой batch с sweep_again_seconds — когда спросить снова
агент  → sweep_result: answers[] {target_id, generation, state: available | unavailable}
```

- выдача — одна транзакция `FOR UPDATE SKIP LOCKED`: самые давно не проверенные (непроверенные первыми),
  семейство по `can_ipv4`/`can_ipv6` агента, прошлой проверке не меньше `pulse_sweep_interval`, без живой
  чужой аренды; ставится аренда и поднимается `lease_generation`;
- срок аренды = 2 × ⌈batch/parallel⌉ × probes × timeout, не меньше 1 с;
- ответ принимается, только если совпали цель, агент, поколение, аренда не истекла и цель не осиротела;
  принятый ответ снимает аренду;
- обрыв сессии — невыполненные аренды этой сессии (с их поколениями) сразу возвращаются в очередь;
- пустая пачка: `sweep_again_seconds` считает база (позднее из «созрела по кругу» и «кончилась чужая
  аренда»), но не больше 60 с: сервер агентов не будит, и новый адрес не должен ждать целый круг; параметров в `settings` ещё нет — «приходи позже» (`retry_min`); у агента нет ни IPv4, ни IPv6
  — 0, в этой сессии обзора не будет.

Агент мерит только **ICMP** (агент без ICMP в Pinger не участвует), с параллельностью из пачки, до
`probes` попыток: ответ — `available`, нет ответа — `unavailable`. Нет маршрута к адресу (`RoutableTo`) или
пробу нельзя выполнить — ответа нет вовсе, аренда истечёт, цель проверит кто-то другой. `unknown` агент
не шлёт: это состояние сервера (не проверяли, некому проверить AAAA).

Состояние цели — **последняя фактическая проверка, оно не протухает**. Голосования нет: цель в цикле
проверяет один агент. `pulse_sweep_interval` означает «не чаще», а не «хотя бы раз в».

**Параметры** (Settings → Pinger & Pulse, карточка Pinger; строки `settings` создаются панелью при первом
чтении или полном пересборе, демон своих значений по умолчанию не имеет):

| Ключ | По умолчанию | Пределы |
|------|--------------|---------|
| `pulse_sweep_interval`, с | 3600 | 60…86400 |
| `pulse_sweep_batch` | 20 | 1…500 |
| `pulse_sweep_parallel` | 4 | 1…64 |
| `pulse_sweep_probes` | 2 | 1…10 |
| `pulse_sweep_timeout_ms` | 1000 | 100…10000 |
| `pulse_history_days` (карточка History) | 90 | 1…3650 |

Карточка **New check defaults** (`pulse_check_interval`, `_timeout_ms`, `_probes`, `_ok_probes`,
`_fail_runs`, `_ok_runs`) — заготовка для новой проверки; существующие проверки не меняет.

**В зоне** видна только проблема: у значения адреса в состоянии `unavailable` — красная точка («No ICMP
reply since …»), щелчок открывает историю записи на вкладке Pinger. Фильтры таблицы записей: Pulse
(`off / default / rule / held`) и Pinger (`unavailable / available / not checked`), по `data-*` строки.

**История записи** — окно с вкладками **Changes** (аудит), **Pulse** (что публиковал Pulse и почему,
`pulse_rule_events`; только у типов Pulse) и **Pinger** (по полоске на адрес, обрезанной интервалами
ссылок, и одна таблица переходов с отбором по адресу; только A/AAAA). Pinger видит каждый, кому видна
зона (`GET /pulse/zones/N/rrset/sweep`); всё остальное в NS Pulse требует `pulse.manage`.

(`/run/dns-panel/pulse`, `root:www-data 0770`); сокет — `0660` с группой `[control] group`.

**Управляющий сокет** — одна JSON-строка на соединение, ответ `{"ok":true|false,"error":…}`:

| Команда | Кто шлёт | Действие |
|---------|----------|----------|
| `{"cmd":"recompute","rule":N}` (`0` — все) | панель | пересчитать правило(а) |
| `{"cmd":"sweep","zone":N}` | панель | догнать список целей Pinger |
| `{"cmd":"activate"}` / `{"cmd":"deactivate"}` | `dns-ha-agentd` | смена роли (§5) |

Сигнал панели — «выстрелил и забыл»: его неудача не проваливает сохранение.

**`pulse-apply.pl`**: `--rule N [--branch M] [--reason "…"]` — переключить (без `--branch` — основной
набор); `--rule N --verify` — сверить зону. Ответ — одна строка JSON (`ok`, `changed`, `state`, `held`,
`ha`, `error`), код 0 — сделано или нечего менять, 1 — отказ.

**API** — `/dns-api/pulse/*` (`www/API/Router.pm`), право `pulse.manage` (кроме `rrset/sweep`): `GET /pulse`,
тестеры (`approve`, `PUT`, `DELETE`), группы и состав, проверки и назначение (`PUT /checks/N/groups`
с `groups` и необязательным `agents`), правила (`POST /rules`, `PUT /rules/N`, `PUT /rules/N/branches`,
`POST /rules/N/clone`, `DELETE`), `GET /pulse/history`, `GET /pulse/zones/N/rrset[/history|/sweep]`,
`PUT /pulse/settings`, `PUT /pulse/server/address`, `POST /pulse/enrollment/key`. Удаление проверки или
тестера возвращает `affected_rules`.
