# dns-watcher — проба готовности пары → действие, там где нет Cisco IP SLA

У HA-пары в режиме **Anycast** контракт с сетью один: **проба готовности** (TCP, по умолчанию `17900`)
открыта только у ACTIVE и только пока он готов обслуживать. Сервисный адрес (`/32` на `lo`) висит на обоих
узлах; куда ему вести, решает внешняя сеть по пробе. Панель и HA-демоны об этой сети не знают ничего.

`dns-watcher` — один из способов эту пробу исполнить. Сам он не знает ни про маршруты, ни про NAT, ни про DNS:
он сводит пробу двух узлов к одному состоянию и при его смене выполняет правило из конфигурации. Что делает
правило — маршрут, nftables, iptables, BIRD, свой скрипт — решает тот, кто его пишет.

| чем исполняется проба | где |
|---|---|
| **Cisco IP SLA + track + static route** | маршрутизатор в каждом DC — рабочий вариант, пример ниже |
| **dns-watcher → маршрут `/32`** | хост, через который клиенты ходят к адресу, или сам клиент |
| **dns-watcher → NAT (nftables / iptables)** | отдельный хост в сети клиентов, когда маршрутизировать нечем; хост — единственная точка отказа |
| **dns-watcher → BIRD** (`birdc enable/disable`) | Linux-маршрутизатор с BGP в каждом DC — анонс `/32`, пока готов свой узел |

HAProxy (community) сюда не подходит: UDP он не проксирует, а DNS — это прежде всего UDP. Keepalived/IPVS —
балансировщик перед DNS, а не anycast: адрес живёт на балансировщике, и в межDC-схеме он сам становится тем
узлом, отказа которого пара должна избегать. BIRD проверять произвольный TCP-порт не умеет — поэтому он в
паре с watcher'ом.

## Состояния и правила

Каждые `interval` — TCP connect к пробе обоих узлов. Узел готов после `rise` удачных проверок подряд и
перестаёт быть готовым после `fall` неудачных — одна случайная потеря пакета трафик не переключает (как у
IP SLA/HAProxy). Отсюда одно из состояний:

| состояние | когда |
|---|---|
| `node1_up` / `node2_up` | готов ровно этот узел |
| `both_down` | не готов ни один |
| `both_up` | проба открыта у обоих — **split-brain**; направлять трафик на одного из двух «активных» наугад значит выбрать, чьи записи потеряются |
| `stop` | (необязательно) watcher останавливается (`SIGTERM`/`SIGINT`) |

`[conditions]` назначает каждому состоянию правило, правило — это секция со списком `commands`:

```toml
address    = "10.0.0.53"
node1      = "10.0.0.11"
node1_port = 17900
node2      = "10.0.0.12"
node2_port = 17900

[conditions]
node1_up  = "ACTIVE"
node2_up  = "ACTIVE"
both_down = "WITHDRAW"
both_up   = "SPLIT"
stop      = "WITHDRAW"

[ACTIVE]
commands = [
  "ip route replace $ADDRESS/32 via $ACTIVE_NODE",
]
```

- правило выполняется **только при смене состояния**;
- команды — через `/bin/sh -c`, **строго по порядку**; первая неудачная останавливает правило, оно не считается
  применённым и повторяется на следующем круге, пока не пройдёт;
- значения для команд берутся **явно из конфигурации**, ничего не угадывается по интерфейсам хоста:

  | переменная | откуда |
  |---|---|
  | `$ADDRESS` | `address` — сервисный адрес пары, без маски (маску команда пишет сама: `$ADDRESS/32`) |
  | `$WATCHER_NODE` | `watcher_node` — адрес этого хоста, на котором ловить трафик (NAT) |
  | `$NODE1`, `$NODE1_PORT`, `$NODE2`, `$NODE2_PORT` | `node1`, `node1_port`, `node2`, `node2_port` |
  | свои | секция `[variables]`, например `DEVICE = "eth0"` → `$DEVICE`; имена из этой таблицы в ней запрещены |
  | `$STATE` | текущее состояние (`node1_up`… `stop`) |
  | `$ACTIVE_NODE`, `$ACTIVE_PORT` | готовый узел при `node1_up`/`node2_up`; пусто при `both_*` и `stop` |

  поэтому одно правило `ACTIVE` обслуживает оба узла, а смена адреса — одна строка в файле;
- `command_timeout` (по умолчанию `10s`) — предохранитель: зависшая команда убивается вместе со своими
  процессами, правило повторится на следующем круге; иначе один зависший `birdc` остановил бы и проверки, и
  обработку остановки;
- удачные команды молчат (писать в журнал правило может само, `logger`); неудача пишется один раз, с выводом
  команды;
- команды выполняются от root, поэтому watcher не запустится, если файл конфигурации принадлежит не root
  или доступен на запись группе и остальным.

Готовые варианты — в [`etc/dns-watcher.example.toml`](../../../../etc/dns-watcher.example.toml): маршрут (включён),
NAT через nftables и через iptables, BIRD (закомментированы).

## Маршрут

```
клиент ──► этот хост ── ip route 10.0.0.53/32 via <ACTIVE> ──► ACTIVE (адрес на lo) :53 / :80
```

Клиенты должны ходить к сервисному адресу **через** этот хост (он их маршрутизатор) — или этим хостом должен
быть сам клиент. Ноутбук разработки:

```bash
sudo bin/dns-watcher -config etc/dns-watcher.toml     # файл — владелец root, без записи для группы и остальных
dig @10.0.0.53 example.com SOA
curl http://10.0.0.53/
```

## NAT

```
клиент ──► $WATCHER_NODE (адрес этого хоста, например 10.0.0.250 на eth0) ── DNAT ──► ACTIVE :53 udp/tcp, :80
```

Когда маршрутизировать нечем: клиенты ходят к адресу этого хоста как к обычному адресу своей сети. Правило
включает `ip_forward`, ставит DNAT с `$WATCHER_NODE` на `$ACTIVE_NODE` с masquerade и сбрасывает conntrack к
адресу — иначе уже открытые потоки ходили бы к прежнему узлу. В варианте nftables таблица объявляется и
правила заменяются одной транзакцией: повторные переключения идут тем же правилом, промежутка без правил нет.

Из-за masquerade узел видит клиентом адрес этого хоста, а не настоящего клиента: это касается журнала панели и
ACL PowerDNS — трансферы зон через такой адрес не пускать. Адрес `$WATCHER_NODE` — обычный адрес этого хоста,
правила его не трогают: при `both_down` запрос к нему получает отказ сразу, а не уходит в никуда.

## Установка

Watcher ставится не на узлы пары, а на хост, через который клиенты ходят к сервисному адресу (или на сам
клиент). У него свой пакет, `dns-panel-watcher_<версия>_amd64.deb` из релиза; под root:

```bash
apt install ./dns-panel-watcher_1.0.0_amd64.deb
install -m 0600 /opt/dns-panel/etc/dns-watcher.example.toml /opt/dns-panel/etc/dns-watcher.toml   # поправить узлы и правила
systemctl start dns-watcher
journalctl -u dns-watcher -f
```

Пакет включает юнит; он стартует, когда есть `etc/dns-watcher.toml` (конфига в пакете нет, так что обновление его не
трогает). Из исходников: `make -C src/dns-watcher build` → `bin/dns-watcher`.

Юнит — `Type=notify`: `systemctl start` возвращается, когда выполнено первое правило. Узлы и порт пробы — те
же, что в конфигурации пары (High availability → Anycast): watcher ничего не спрашивает у панели.

## Cisco: то же самое на маршрутизаторе

```
ip sla 1
 tcp-connect 10.0.0.11 17900
 frequency 5
ip sla schedule 1 life forever start-time now
track 1 ip sla 1 reachability
!
ip sla 2
 tcp-connect 10.0.0.12 17900
 frequency 5
ip sla schedule 2 life forever start-time now
track 2 ip sla 2 reachability
!
ip route 10.0.0.53 255.255.255.255 10.0.0.11 track 1
ip route 10.0.0.53 255.255.255.255 10.0.0.12 track 2
```

В разных DC у каждого маршрутизатора — свой узел и свой track; маршрут `/32` дальше распространяется тем
протоколом, который уже есть в сети. При split-brain Cisco с двумя tracked-маршрутами разложит трафик на оба —
в отличие от правила `both_up` у watcher'а.
