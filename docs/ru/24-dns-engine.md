# 24. Движок DNS: почему PowerDNS + gmysql

На чём панель стоит, почему так и при каких условиях к вопросу вернёмся.

## Решение

**PowerDNS Authoritative + backend `gmysql`**. Панель работает с базой `pdns` напрямую (SQL) там, где нужна
атомарность и полнота операции, и через **HTTP API PowerDNS** там, где это его собственное состояние: кэш,
смена kind, TSIG-ключи, DNSSEC-ключи и rectify, часть метаданных. Немедленные действия после записи
(`purge`, `notify`, `retrieve`, `rediscover`) идут через `dns-agent` — управляющий сокет PowerDNS.

Чего нет: backend `remote`, второго движка рядом, собственной копии зон в базе панели, публикатора-посредника.

## Почему не только API

- **`AXFR-MASTER-TSIG`** metadata-эндпоинт API не обслуживает (ответ 422). Поэтому источник secondary-зоны
  меняется одной SQL-транзакцией — адреса, `last_check` и ключ вместе (`zone_secondary_source_set`): порознь
  любой сбой между шагами оставлял бы новый ключ при старом адресе — зону, которая молча не едет. Кэш зон
  снимает `rediscover` после транзакции.
- **Атомарности между шагами API нет.** Смена роли на secondary — это одновременно тип зоны, адреса primary,
  ключ, обнуление `last_check` и стирание местных записей. Через API это несколько независимых запросов, и
  между ними PowerDNS успел бы получить зону с новым источником, а запоздавшее стирание снесло бы **уже
  приехавшие** записи. Одной транзакцией в базе это одно изменение, и PowerDNS узнаёт о новой роли после неё.

Правило: **прямой SQL там, где операция обязана быть атомарной или где API не умеет нужного поля; API там,
где речь о собственном состоянии PowerDNS.**

## Кто чем владеет

| Зона | Кто пишет содержимое | Что делает панель |
|------|----------------------|-------------------|
| Primary (`MASTER`/`NATIVE`) | панель | правит записи, ведёт serial, ключи DNSSEC, показывает историю |
| Secondary (`SLAVE`) | PowerDNS по AXFR от чужого primary | правит только **источник** (адреса, TSIG) и прямую раздачу вниз; записи read-only |

Secondary-зону можно раздавать вниз прямым списком, но не каталогом: producer объявляет только собственные
зоны сервера (см. [16-delivery.md](16-delivery.md), [05-dns-model.md](05-dns-model.md)).

## Обязанности панели при прямом SQL

Пишем в чужую схему — значит берём на себя то, что иначе сделал бы сервер:

- **Корректность данных.** Тип, содержимое и имя проверяются до записи (`dns_validate`,
  `dns_record_name_norm`): имя приводится к одному виду (без завершающей точки, кроме корня), битые имена
  отвергаются, а не «чинятся».
- **Транзакции и порядок блокировок.** Любая правка — одна транзакция. Порядок общий: строки `domains` по
  возрастанию `id` (`SELECT … FOR UPDATE`), затем SOA-строки, затем записи. Один порядок во всех путях —
  иначе две операции над одной парой зон встают друг против друга.
- **Роль проверяется под блокировкой.** Ранняя проверка даёт понятную ошибку до всякой работы, но решает
  проверка **внутри транзакции** (`_lock_zones_writable`): пока правка ждала очереди, зона могла стать
  secondary, и правку снёс бы первый же AXFR. Удаление зоны тоже берёт строку `domains` первой. Создание
  зоны с делегированием блокирует и проверяет родителей до любой записи; отказ полный.
- **Serial.** Каждая транзакция поднимает serial ровно один раз, на уже заблокированной SOA-строке.
- **Действия после записи.** PowerDNS о правке в базе сам не узнаёт: панель делает rectify подписанной зоны,
  `purge` (кэш), `notify` (получатели) и, для secondary, `retrieve` через `dns-agent`, а исход запоминает в
  `zone_sync_state`.
- **Совместимость со схемой.** Пишем только в таблицы gmysql (`domains`, `records`, `domainmetadata`; при
  удалении зоны ещё `comments`, `cryptokeys`) и в тех же полях, что и сервер; единственное расширение —
  `records.updated_by`/`updated_at` ([03-database.md](03-database.md)). Схема PowerDNS может измениться в новой
  мажорной версии — проверять её надо при обновлении.

**Граница.** Блокировки упорядочивают операции панели: правка ↔ смена роли ↔ удаление зоны. Сам PowerDNS
(идущий AXFR, собственные метаданные вроде `CATALOG-HASH`) пишет в базу своим чередом и этими блокировками не
управляется: между удалением зоны в SQL и сообщением об этом PowerDNS демон может дописать строку про зону, которой уже нет.
Если там обнаружится проблема, её чинят отдельно, а не расширением этого механизма.

## Что рассмотрели и отвергли

- **Backend `remote`** (PowerDNS спрашивает панель на каждый запрос). Панель встаёт в путь разрешения имён:
  её падение становится отказом DNS, а не интерфейса. Сейчас панель может лежать, а сервер отвечает.
- **Цепочка DNS-серверов** (панель пишет в свой сервер, тот отдаёт дальше). Ещё один узел в сопровождении
  ради задачи, которую решает транзакция в базе.
- **Копия всех записей в базе панели** (панель — источник истины, PowerDNS — производная). Две копии
  расходятся, и появляется вопрос, какая правее. Источник истины один: база PowerDNS.

Отвергнуто по цене сопровождения, а не по принципу.

## Когда вернёмся к сравнению движков

Повод — конкретная потребность:

- нужны сотни зон, правящихся одновременно, и упирается именно движок или его база;
- обновление PowerDNS ломает схему `gmysql` так, что прямой SQL перестаёт быть посильной ценой;
- появляется требование, которого у PowerDNS нет вовсе (специфический тип данных, собственная логика ответа).
