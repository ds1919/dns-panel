# 01 — Обзор и цели проекта

## Зачем

DNS-сеть работает на **BIND** со старой самописной панелью (PHP + Python) в LXC на устаревшем Debian,
которую невозможно обновить. Проект заменяет мастер и панель:

- **Shadow-master на PowerDNS** — скрытый авторитативный мастер: не публикуется в NS-записях и не
  обслуживает публичные запросы. Хранит зоны в MySQL (`gmysql`) и рассылает NOTIFY.
- **Secondary остаются на BIND** — публичные серверы имён, забирают зоны с shadow-master по AXFR.
- **Своя панель** поверх PowerDNS. Готовые (напр. PowerDNS-Admin) избыточно сложны, поставляются в Docker и
  написаны на Python — нам это не подходит.

Зоны со старого мастера переносятся панелью — [26-zone-import.md](26-zone-import.md).

## Принципы

1. **Данные зон живут в PowerDNS** (`domains`, `records`, `domainmetadata`, `cryptokeys`). Панель — редактор
   поверх них и не держит их копий.
2. **Своя БД — только своё:** пользователи, права, аудит, раздача, профили, метки, NS Pulse
   ([03-database.md](03-database.md)).
3. **Без тяжёлого фронтенда.** Серверный рендер + точечный AJAX; без SPA-фреймворков и сборки.
4. **Без Python и Docker.** Деплой — дерево файлов в `/opt/dns-panel`, Apache + `mod_fcgid`, systemd-юниты
   Go-демонов.
5. **Любая правка данных зоны инкрементит SOA serial** — иначе secondary не обновятся.

## Область

- Внутренние и внешние зоны, поддомены и делегирование, обратные зоны и PTR.
- Security-записи (CAA, TLSA, SSHFP, SPF/DKIM/DMARC и т.п.).
- Secondary-зоны: PowerDNS сам тянет зону с внешнего мастера и отдаёт её дальше.
- Раздача зон на secondary: прямая и через каталоги RFC 9432 ([16-delivery.md](16-delivery.md)).
- DNSSEC: подпись, управление ключами, перенос подписанных зон с их ключами.
- Dynamic DNS (RFC 2136 UPDATE от DHCP по TSIG).
- HA-пара с ручным switchover ([22-ha-contract.md](22-ha-contract.md)).
- NS Pulse: переключение записей по результатам внешних проверок ([25-ns-pulse.md](25-ns-pulse.md)).

Модель зон и записей — [05-dns-model.md](05-dns-model.md).
