# 05 — Модель зон и записей

Что панель моделирует и как.

## Типы зон (`domains.type`)

| Тип | Смысл у нас |
|-----|-------------|
| `MASTER` (Primary) | Зона, для которой наш PowerDNS — источник. Правим в панели, рассылаем NOTIFY. Основной случай. |
| `SLAVE` (Secondary) | PowerDNS сам забирает зону по AXFR с чужого primary (`domains.master`). Записи read-only, панель правит только источник. |
| `NATIVE` | Панель такие зоны **не заводит** (Add zone — только Primary и Secondary). Существующую NATIVE-зону показывает как есть и умеет сделать её Secondary. AXFR наружу PowerDNS для NATIVE отдаёт, но NOTIFY не рассылает и в каталог её не берёт (`gmysql-info-all-primary-query` фильтрует `d.type in ('MASTER','PRODUCER')`): downstream узнает об изменении только по SOA-refresh. |

### Secondary: раздача вниз

Secondary-зону можно отдавать своим получателям прямым списком (`zone_direct_axfr`) — это свойство зоны,
а не роли. Для неё панель ставит `SLAVE-RENOTIFY`, иначе PowerDNS не шлёт NOTIFY вниз после приёма. В
каталог secondary не берётся: PRODUCER объявляет только собственные зоны сервера. Подробно —
[16-delivery.md](16-delivery.md).

### Secondary: откуда и когда приезжает

Блок Secondary на странице зоны показывает upstream, TSIG, serial и состояние трансфера; в его шапке две
кнопки. **Edit upstream** (`PUT /zones/:id/secondary-source`) меняет адреса primary и ключ. **Refresh AXFR**
(`POST /zones/:id/refresh-axfr`, write-доступ к зоне) просит PowerDNS забрать зону заново —
`pdns_control retrieve` один раз, даже если зона уже Active; Edit upstream после сохранения делает то же.
Этим кнопка отличается от Retry now в баннере проблем: тот просит трансфер, только пока зона не приехала.
Явный запрос обходит и бэкофф PowerDNS после отказов мастера.

Ответ — «AXFR запрошен», а не «приехал». Приезд — это `domains.last_check` (Last check в блоке): его ставит
PowerDNS после удачной сверки с primary, а смена источника и Make secondary обнуляют. Secondary считается
Active, только когда она отдаётся **и** сверена с текущим primary; ожидание дальше ведёт worker. В журнале —
`refresh_axfr`.

### Динамические обновления (RFC 2136)

Приём включают в Zone settings (Dynamic updates: On / Off, у secondary — заранее). Кто вправе обновлять зону
(обычно DHCP) — **свойство самой зоны**: кнопка **Dynamic updates** в шапке зоны (есть, только когда приём
включён), отдельная модалка; флаг она не трогает. Там адреса DHCP-серверов и/или **один** TSIG-ключ (имя,
алгоритм, секрет — как `key "…" { algorithm …; secret "…"; }` в BIND; ключ виден открыто, есть Generate).
Режим следует из заданного:

| Задано | ALLOW-DNSUPDATE-FROM | TSIG-ALLOW-DNSUPDATE |
|--------|----------------------|----------------------|
| адреса | адреса DHCP | — |
| ключ | `0.0.0.0/0`, `::/0` (адрес любой) | ключ |
| оба | адреса DHCP | ключ |

Одинаковые настройки многих зон — **Dynamic DHCP profile** (Settings → Dynamic DHCP profiles). Зона может ему
**следовать** («Follow profile changes»): правка профиля доезжает до всех таких зон и сразу до PowerDNS. Правка
любого поля в зоне или снятая галочка связь снимают — значения остаются. «Save as profile» — из настроек зоны.
Удаление профиля оставляет зонам их значения. Значения лежат у зоны всегда (`zone_dynamic` +
`zone_dynamic_sources` / `zone_dynamic_keys`), профиль — `dyn_profiles` + свои адреса/ключ.

Имя ключа в PowerDNS одно на всю установку. То же имя с тем же секретом — тот же ключ; с другим секретом —
**смена ключа** (журнал: `tsig_key_update`), и она разрешена, только если ключом пользуются лишь те, кого
правка касается: профиль и зоны, которые ему следуют, или одна эта зона. Держит ключ ещё кто-то — отказ,
нужно другое имя. Worker на каждом проходе сверяет с PowerDNS и ключи dynamic-зон и профилей. Ключ уходит
сам, когда на него больше никто не ссылается. `NOTIFY-DNSUPDATE` ставится всегда — иначе secondary не узнали
бы об обновлении. Serial PowerDNS увеличивает сам.

Приём — только у primary. Add zone и Reverse предлагают сразу следовать профилю. У secondary настройки задают
заранее — начнут действовать после Make primary; перенесённую dynamic-зону (`X-DNSPANEL-IMPORT-DYNAMIC`) Make
primary повышает только с приёмом и только когда настройки уже заданы, пометку переноса снимает. Make
secondary приём выключает (настройки остаются). Флаг и значения — намерение: если API PowerDNS не ответил,
их доводит worker.

**pdns.conf при работе не трогается и PowerDNS не перезапускается.** При установке: `dnsupdate=yes`,
**пустой** `allow-dnsupdate-from` (глобальный список складывается с зоновым) и `forward-dnsupdate=no`
(`docs/INSTALL/reference/03-powerdns.md`).

### DNSSEC

Подписывает PowerDNS сам, на лету, из своих ключей; панель ими управляет. Кнопка **DNSSEC** в шапке
primary-зоны: подписать одним CSK (по умолчанию `ECDSAP256SHA256`), добавить ключ (сгенерировать или
импортировать BIND `.private`), Activate/Publish, удалить, снять подпись; DS для родителя (SHA-256)
показывается у KSK/CSK. API: `GET|PUT /zones/:id/dnssec`, `POST /zones/:id/dnssec/keys`,
`PUT|DELETE /zones/:id/dnssec/keys/:kid`. Каждая смена ключей поднимает serial.

Записи пишутся SQL-ем, поэтому у подписанной зоны после каждой записи нужен rectify: он делается внутри
`zone_sync_verify`, и неудача считается неудачной активацией (её повторит worker). Данные подписи в списке
записей не показываются и не считаются. Перенос подписанной зоны со старого сервера с её ключами —
[26-zone-import.md](26-zone-import.md).

### Смена роли зоны

Роль меняется в обе стороны, в одном месте — Zone settings самой зоны.

| Операция | Что делает |
|----------|-----------|
| **Make primary** (`POST /zones/:id/promote`) | `SLAVE` → `MASTER`. Записи и SOA serial остаются, upstream и его TSIG снимаются. Требует, чтобы зона уже приехала: у зоны без SOA получилась бы пустая авторитативная. |
| **Make secondary** (`POST /zones/:id/demote`) | `MASTER`/`NATIVE` → `SLAVE`. Нужны адреса primary (хотя бы один) и, по желанию, TSIG. Записи дальше приезжают по AXFR и вручную не правятся. |

Обе подтверждаются именем зоны на API (`confirm_name`). В интерфейсе имя вводят только у **Make secondary**:
там записи зоны заменяются приехавшими, а у Make primary они остаются на месте.

Прямую раздачу смена роли не трогает. Каталог — трогает: `Make secondary` снимает зону с каталога
(PRODUCER объявляет только собственные зоны); форма говорит об этом до нажатия, а на API снятие требует ещё
`distribution.manage`.

**Местные записи при Make secondary стираются**: содержимое у primary, и пока передача не пришла,
отдавать нечего — «зона отдаётся» означает ровно «зона приехала». Тип, адреса primary, ключ, обнуление
`last_check` и стирание записей — ОДНА транзакция в базе PowerDNS, и только после неё PowerDNS о новой роли
узнаёт (почему — [24-dns-engine.md](24-dns-engine.md)).

Адреса primary и ключ в обеих операциях проверяет одна функция `_secondary_source_fields`, а правку источника
у существующей secondary пишет `zone_secondary_source_set` — одной транзакцией.

## Внутренние vs внешние домены

Отдельного признака «internal/external» у зоны нет — он ничего не решал бы в DNS. Вопрос распадается на три:

1. **Разные NS/SOA/каталог → разные профили** («FXTM Internal» и «FXTM External»). Профиль — один пресет,
   в нём же каталог по умолчанию. Нужен при создании primary — это её начальные SOA/NS; после создания
   профиль — необязательная привязка (`X-DNSPANEL-PROFILE`), её можно снять (`None`). У secondary SOA и NS
   приезжают по AXFR, профиль ей не нужен.
2. **Признак для глаз и фильтров → метка** (Labels, например категория `Scope` со значениями
   `Internal`/`External`).
3. **Кто на самом деле получает зону** решает раздача (Propagation/Catalog) — единственное место, где такое
   решение имеет силу.

## Поддомены и делегирование

- Поддомен внутри той же зоны — просто записи с `name` вида `sub.example.net`.
- Делегирование в отдельную зону — `NS`-записи в родителе + отдельная зона. Создание зоны с делегированием
  пишет NS в родителя в той же транзакции (и поднимает его serial); окно удаления зоны называет её
  делегированные дочерние зоны.

## Типы записей

Разрешённые типы (`dns_validate`): `A`, `AAAA`, `CNAME`, `MX`, `TXT`, `NS`, `PTR`, `SRV`, `CAA`, `TLSA`,
`SSHFP`, `SPF`, `NAPTR`, `DNAME`, `DS`; `SOA` правится отдельно. У `MX`/`SRV`/`CAA` форма собирает `content` из
полей, у остальных — одно значение с проверкой формата. DNSSEC-записи самой зоны (`DNSKEY`, `RRSIG`, `NSEC*`,
`CDS`/`CDNSKEY`) ведёт PowerDNS, вручную они не заводятся.

## SOA и serial

- Формат `content`: `primary hostmaster serial refresh retry expire minimum`.
- Дефолты новых зон (NS/hostmaster/SOA-таймеры) — в `zone_profiles` (Settings → Zone profiles); без профиля
  NS и hostmaster берутся из формы, таймеры стандартные. Serial новой зоны — `YYYYMMDD01`.
- **Любая правка данных зоны поднимает serial ровно один раз** (внутри `pdns_apply_rrsets`), иначе
  secondary не заберут изменения.

## NOTIFY / AXFR

Кому отдаётся зона и кому уходит NOTIFY, панель пишет в метаданные зоны (`ALLOW-AXFR-FROM`,
`TSIG-ALLOW-AXFR`, `ALSO-NOTIFY`) из прямого списка и каталога — [16-delivery.md](16-delivery.md).
