# 22 — HA-контракт (правила)

Что HA-контур гарантирует. Как это реализовано — [23-ha-manager.md](23-ha-manager.md) (ссылки на разделы ниже),
размещение в проде — [13-ha-topology.md](13-ha-topology.md).

HA не обязателен: одиночный узел работает без него.

## 1. Режимы узла

- `[ha] enabled = true` в `panel.toml` означает только «HA-контур установлен на этом узле». Без него узел —
  standalone: manager не спрашивается, write-gate пропускает всё, `/health/ready` проверяет только локальные
  зависимости.
- С установленным контуром есть ли пара, отвечает manager: `ha_configured` = `true` / `false` / `null`.
  `false` (нет ревизии, в т.ч. после роспуска) — узел работает как одиночный. `null` — «неизвестно», и это
  не «HA выключен»: запись запрещается.
- Состояния Standalone → Paired · HA not configured → Paired · HA active — [23 §1](23-ha-manager.md#1-состояния-узла).

## 2. Единственный писатель

- В паре ровно один ACTIVE: MariaDB `read_only=0`, PowerDNS `primary=yes secondary=yes`, сервисный адрес
  опубликован. STANDBY: `read_only=1`, PowerDNS `no/no`, асинхронная реплика ACTIVE.
- Роль определяется правом быть ACTIVE (durable-доказательство в safety-файле узла), а не строкой в базе.
  Право выдаётся только создание пары, передача при плановом переключении или оператор при аварии
  ([23 §3](23-ha-manager.md#3-право-быть-active)).
- **Физика.** `read_only` защищает данные независимо от решений софта: учётки панели и PowerDNS не имеют
  `SUPER`/`READ ONLY ADMIN`. Право и физика сверяются независимо; расхождение — признак split-brain, запись
  запрещается.
- Узел пары после рестарта MariaDB стартует read-only (fail-safe) и возвращает себе роль только с
  доказательством ([23 §8.3](23-ha-manager.md#83-остаться-active--стать-active)).
- Epoch монотонен; узел, увидевший у соседа больший epoch, уходит в безопасное состояние; команды из
  прошлого epoch не исполняются.

## 3. Плановое переключение

Смена ролей двух **живых** узлов; старый ACTIVE не выключается и становится STANDBY.

1. Запускается на ACTIVE; target — здоровый STANDBY с той же конфигурацией пары, не огорожен, репликация
   работает.
2. Сначала source перестаёт писать и публиковаться, и `read_only=1` доказывается наблюдением.
3. Затем target доказанно применяет всё до GTID-позиции source — единственное доказательство отсутствия потерь.
4. Только после этого source передаёт право (новый epoch = текущий + 1) и отказывается от своего — точка
   невозврата. До неё любой отказ отменяет операцию, и source остаётся ACTIVE; после — операция не
   откатывается, а доводится.
5. Source пропал до передачи права — target сам не повышается.
6. Пока идёт операция, запись закрыта, узел не готов принимать трафик.

Шаги — [23 §9](23-ha-manager.md#9-плановое-переключение).

## 4. Аварийное повышение

1. Только решением человека, никогда автоматически: два узла не отличают «сосед умер» от «сеть порвалась».
2. Основание — типизированное подтверждение, что прежний ACTIVE остановлен, плюс автор; оба записываются.
3. Отказ, если сосед отвечает и обслуживает трафик: это плановое переключение.
4. Новый epoch, право и огораживание прежнего ACTIVE записываются до того, как узел станет writable.
5. Полученный, но не применённый relay log сначала применяется; продолжить без доказательства — только с
   явным согласием на потерю данных.
6. Огороженный узел сам не повышается и не подключается репликой; в пару возвращается только пересевом,
   огораживание снимает ACTIVE.

Шаги — [23 §10](23-ha-manager.md#10-аварийное-повышение-и-пересев).

## 5. Split-brain без арбитра

Witness, кворума и автоматического арбитража нет. Безопасность дают порядок (demote и drain до передачи
права), физика `read_only`, монотонный epoch, огораживание и человек в аварийном пути.

При разрыве связи ACTIVE продолжает обслуживать (`ha_healthy=false`), STANDBY не повышается. Цена: огороженный,
но включённый прежний ACTIVE, до которого нет связи, продолжает обслуживать; при первом контакте он видит
больший epoch или своё огораживание и уходит в безопасное состояние.

## 6. Write-gate панели

`ha_write_verdict` (`www/include/functions.pm`) — на каждый мутирующий запрос:

| условие | ответ |
|---|---|
| HA не установлен | разрешено |
| manager не отвечает | `503 ha_manager_unavailable` |
| `ha_configured = null` | `503 ha_state_unknown` |
| `ha_configured = false` | разрешено |
| роль `unknown` | `503 ha_role_unknown` |
| не ACTIVE | `409 standby_read_only` |
| у узла идёт HA-операция | `409 writes_frozen` |
| локальный `read_only` не прочитан / база недоступна | `503 ha_read_only_unknown` / `503 ha_db_unavailable` |
| ACTIVE, но `read_only=1` | `503 ha_role_mismatch` |

Где применяется: `api.pl` — все `POST/PUT/PATCH/DELETE` после аутентификации и CSRF; MCP
(`www/mcp/dns-mcp.pl`) — не-readonly инструменты; фоновые задачи (`libexec/sync-task.pl` через `ha_gate_action`:
`standby_read_only`/`writes_frozen` → пропустить, прочие отказы → ошибка).

Исключения в `api.pl` (у manager'а свой, более строгий gate; аутентификация, CSRF и право остаются):
`POST ha/switchover`, `ha/emergency`, `ha/reseed`, `ha/operations/:id/resume`,
`ha/pair/{create,join,approve,reject,reset,build}`.

Отдельного флага «freeze» нет: запись закрыта, пока в журнале manager'а у узла есть операция. При каждой
смене «ACTIVE и нет операции» manager будит `dns-sync-worker`.

## 7. Панель на узле пары

- **Адреса.** Рабочий вход — сервисный адрес пары, он ведёт на ACTIVE. Адреса узлов — управляющие: на STANDBY
  панель показывает состояние и управляет парой, запись отбивает write-gate.
- **Вход на STANDBY невозможен:** сессия — строка в `dns_panel.sessions`, а база read-only. `login.pl`
  отвечает `401` на неверный пароль, `409` с `code` (`standby_read_only` | `ha_role_unknown` |
  `ha_manager_unavailable`) и сервисным адресом, если узел не может создать сессию, `503` на прочие ошибки.
  Та же причина показывается на странице входа заранее.
- **`/health/ready`** (`node_health`): `200` только если готов, иначе `503` с проверками. В паре с включённым
  HA к локальным проверкам (`panel_db`, `schema`, `pdns_db`, `pdns_control`) добавляются ответ manager'а и его
  `service_ready`; во время операции — `switching`; ACTIVE без подтверждения агента — `degraded`; без
  NOTIFY и публикации — `activating`. `/health/live` базу не трогает. Маршрут anycast определяется не
  `/health/ready`, а пробой manager'а ([23 §14.2](23-ha-manager.md#142-anycast-проба-готовности)).
